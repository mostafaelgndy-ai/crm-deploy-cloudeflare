## 7. Resolved Decisions & Technical Notes

### Resolved Decisions

1. **Data layer — localStorage with clean abstraction:**
   The README mentions "coming from the backend (ClaudeFlare OpenNext)" but the prototype uses `localStorage` and no backend/API/database is set up in the project. **Decision:** Use `localStorage` initially (matching the prototype) with a clean abstraction layer (`src/lib/storage.ts`) that can be swapped for API routes later. All storage functions are typed and centralized in one module, so migrating to a real backend only requires replacing `storage.ts` internals.

2. **Route structure — nested routes:**
   The README says `/[cardId]` and `/[ticketId]` (flat), but the prototype uses `/project/ID` and `/ticket/ID` (nested). **Decision:** Use nested routes (`/project/[id]`, `/ticket/[id]`) to avoid ID conflicts between projects and tickets (both use prefixed IDs like `p1`, `t1`) and to match the prototype's routing structure exactly.

3. **Employee status changes — add UI to ticket detail page:**
   The README explicitly states "I can Set the status to 'completed' | 'onGoing'" but the prototype's ticket detail page only has a download button. **Decision:** Add a status change UI to the ticket detail page. The employee can change the status to `completed` or `onGoing` only (via a `<select>` dropdown or button group). When the employee sets status to `completed`, `endsAt` auto-sets to today's date. The admin retains full control over all 4 statuses via the admin ticket form. This is a **new feature not in the prototype** — it's driven by the README requirements.

### Technical Notes

4. **SSR/hydration mitigation:**
   Since the app relies heavily on `localStorage`, there's a risk of hydration mismatches. **Mitigation:** All `localStorage` access must be in `useEffect` or event handlers. The `useAuth` hook reads session in `useEffect`. Protected pages show a loading state during the initial auth check. The `storage.ts` module guards all access with `typeof window !== 'undefined'` checks.

5. **Tailwind v4 font weights:**
   The prototype uses `font-700` and `font-600` classes (non-standard). **Conversion:** Use `font-bold` (700) and `font-semibold` (600) instead, which are standard Tailwind utilities that work in v4.

6. **Arbitrary color classes → theme colors:**
   The prototype uses many arbitrary color values like `text-[#EDEFF3]`, `border-[#2A3240]`. **Approach:** Where a matching theme color exists (e.g., `text-[#EDEFF3]` → `text-paper`, `border-[#2A3240]` → `border-border`), use the theme color. Where no match exists, keep the arbitrary value. This improves consistency and maintainability.
